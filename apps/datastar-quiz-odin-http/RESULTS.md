# Load runs

Measured on **2026-08-31**, on the machine the python numbers in `../datastar-quiz/COMPARISON.md`,
the Go numbers in `../datastar-quiz-golang/RESULTS.md`, the Rust numbers in
`../datastar-quiz-rust/RESULTS.md` and the Tina numbers in `../datastar-quiz-tina/RESULTS.md` were
measured on: 24 cores, Windows, over loopback, load generated by `apps/dsquiz-perf/` (locust) on the
same box.

The harness is **unchanged** — the same one that drove the other four. It reads the mount prefix, the
variant query, the question nonce and the candidate count off the page rather than assuming them, so
one client drives all five servers. What differs is the runtime, not the load.

**The odin-http column is measured here; every other column is quoted.** The python, Go, Rust and
Tina figures are read out of those ports' own result files as they stood on 2026-08-31 — nothing was
re-run side by side. That matters most for the Tina column, because **that port is being actively
worked on** (its `session/` package has already gained the store protocol and the session lease that
phase I needs), so its numbers may move under this table. The shared-source claim that makes the two
Odin ports comparable is pinned to a snapshot and is checkable with one `diff -rq`; README.md, "The
snapshot this is against", has it.

```shell
just dsoh serve-brotli                                    # port 5062, one event-loop thread
DSQUIZ_PERF_HOST=http://127.0.0.1:5062 just dsperf headless 400 20 300
```

Two things to know before reading any number here.

**This port is measured with brotli compiled in** (`-define:DSQUIZ_BROTLI=true`), which is what makes
it comparable to the other four: the same C brotli at quality 5 with a 256-byte minimum that
Litestar, `andybalholm/brotli`, the `brotli` crate and the Tina port were configured with.

**`req/s` in the scenario tables is not a capacity number.** It is set by the scenarios' think time
and by the ~1 s answer choreography. The capacity number is in *"Where this server actually stops"*,
and on this port that section has a different shape from the Tina port's: nothing stopped.

Latency is the Tina port's, to the millisecond, on the same hardware and the same script: P50 1 ms,
P90 2 ms, P95 2 ms, P99 16 ms, zero failures over 24,542 requests. The choreography is paced
correctly — 0.989 s mean against Go's 1.004 s and Tina's 1.029 s, on a script of deliberate sleeps

**Memory is where the two Odin ports separate.** 23.9 MB at rest against Tina's 72.5 MB, and
66.5 MB at 400 players against Tina's 216 MB — a third of it, for the same latency. That is the whole
trade in one row: Tina buys 512 connection slots' worth of egress buffer and route state before the
first request arrives (63 KB + 56 KB each, ~61 MB reserved at boot), and this runtime allocates a
growing arena per connection and frees it when the response is sent.

**At 800 users nothing breaks either.** 30,574 requests, zero failures, the median unmoved at 1 ms,
6,989 SSE streams sampled at a 994 ms mean with none over the 6 s budget. The tail does move — P95
2 → 9 ms, P99 16 → 36 ms — and it moves where one event loop would be expected to queue: `GET /`, the
route that renders and compresses a document per request, goes from P50 2 ms / P95 28 ms to
P50 26 ms / P95 49 ms. That is the honest warning sign, and it is the same one the Tina port shows at
500. This port simply does not fall over after it: the Tina port's equivalent run is a **crash** at
that point, and the next section is where that comparison is made.

The reverse of the trade is that the ceiling is not declared anywhere. It is found under load, and
the next section is that search.

## Where this server actually stops

The Tina port's equivalent section documents a **SIGSEGV above ~500 concurrent users**, reproducible
in ten seconds with `hey -n 6000 -c 300 http://127.0.0.1:5061/` — the index route, the one that
renders a per-request document. That is the first thing this port was pointed at, with the same
command:

```
hey -n  6000 -c  300 http://127.0.0.1:5062/     17,233 req/s, all 200, server alive
hey -n 40000 -c 1000 http://127.0.0.1:5062/     15,742 req/s, all 200, server alive
```

40,000 documents at concurrency 1,000, 801 MB of body, every response a 200, `GET /health` answering
afterwards, and RSS at 71.1 MB. The closed-loop index-route ceiling on one thread is therefore
**~16–17 k documents/second**, which is nowhere near what the scenario runs ask of it.

So this section has no crash in it, and that is the result rather than an absence of one: the same
command, on the same box, against a port that shares every non-HTTP line of source with the one that
faults. Whatever the Tina port's index-route fault is, it is in the HTTP runtime or in this app's use
of it — not in the renderer, the corpus, the engine or the session store, all of which are the same
files here.

Two caveats on that inference, both worth stating rather than burying. The Tina crash was **not
reproduced in this session** — it is quoted from that port's `RESULTS.md`, and that port is under
active edit, so it may already be fixed or may have moved. And "the same files" is true of the
snapshot this port was copied from; its `session/` package has since diverged there. The conclusion
survives both — the fault was bisected in that port to the index route, and the index route's
renderer is byte-identical here — but it is an inference across two trees rather than one
measurement, and only re-running both would make it more than that.

## Pacing, frame by frame

The property the ground rules actually care about is that the toast sequence *arrives* paced rather
than in one burst at the end. Timestamped with `curl`-equivalent streaming (`sse_probe.py`):

```
a WRONG answer                          a CORRECT answer
  +   1.1 ms  signals {"_streak":0}       +   0.8 ms  signals {"_streak":1}
  +   0.0 ms  elements #sfx (clear)       +   0.0 ms  elements #sfx (clear)
  +   0.0 ms  elements #sfx (beat)        +   0.0 ms  elements #sfx (beat)
  +   0.0 ms  elements #toasts            +   0.0 ms  elements #toasts "Correct!"
  + 606.7 ms  elements #toasts (clear)    + 511.3 ms  elements #toasts (+points)
  +   0.0 ms  elements #app (fat morph)   +   0.0 ms  signals {"_points":26,...}
  +   0.0 ms  signals {"_correct":0,...}  +   0.0 ms  elements .candidates (floater)
                                          + 514.0 ms  elements #toasts (+points)
  total 608 ms over 7 events              +   0.0 ms  signals {"_points":52,...}
                                          +   0.0 ms  elements .candidates (floater)
                                          +1503.3 ms  elements #toasts (clear)
                                          +   0.0 ms  elements #app (fat morph)
                                          +   0.0 ms  signals {"_correct":1,...}

                                          total 2,529 ms over 13 events
```

2,529 ms against the Tina port's 2,506 ms and the Go port's 2,513 ms for the same script (0.5 + 0.5 +
0.5 + 1.0 s of deliberate beats). The gaps are the script's own, to within ~15 ms.

**They were not, in the first working build.** The same script ran at 777 / 1000 / 2008 ms — every
pause rounded up to the next second — with no error, no failed request, and a load run that reported
success. The cause is a `core:nbio` sharp edge and it is written up in README.md, "The trap this port
paid for", with the 12-tick repro that pins it:

```
plain      gaps (ms): 110 109 107 108 110 108 110 109 108 109 109 109
with_date  gaps (ms): 114 108 109 111 110 109 109 108 111 109 108 108
after_send gaps (ms): 109 109 785 1010 1013 1015 1013 1001 1005 1003 1015 1001
```

A chained 100 ms `nbio.timeout` is accurate alone and with a 1 s timer beside it, and ten times too
long when re-armed from a **send completion** — because the tick computes its sleep before draining
the completed queue that runs that callback. The fix is in `web/sse.odin`: register the pause
*before* submitting the send, so the timeout is never armed from a completion.

## Per route, head to head — is this faster than the Rust port?

Short answer: **on these routes yes, and mostly not for a reason that says anything about Odin.**

Closed-loop, the method the Tina port's table used so the two are readable together: no think time,
one route at a time, **one reused session**, `hey -n 3000 -c 4`, each route run twice — once with
`Accept-Encoding: br`, once with `identity`. One event-loop thread, release build with brotli
compiled in.

### How to read that table

Each cell is **closed-loop throughput** — requests per second with no think time at concurrency 4 —
not a latency. Turn it into a cost per request with `1e6 / rps` µs, and the whole table becomes
readable:

| route | odin-http br / id / brotli | tina | rust | go |
|---|---|---|---|---|
| `GET /` | 338.4 / **54.8** / 283.6 µs (84%) | 285.3 / **36.1** / 249.2 (87%) | 1047.1 / **91.5** / 955.7 (91%) | 1273.9 / **747.9** / 525.9 (41%) |
| `POST /restart` | 71.0 / **69.3** / 1.7 (2%) | 46.2 / **46.5** / ~0 | 1236.1 / **208.1** / 1028.0 (83%) | 1652.9 / **667.1** / 985.8 (60%) |
| `GET /filter/preview` | 42.4 / **42.3** / 0.1 (0%) | 19.3 / **19.1** / ~0 | 329.5 / **132.0** / 197.5 (60%) | 233.4 / **164.7** / 68.7 (29%) |
| `POST /settings` (204) | 28.5 / **33.2** / — | 18.7 / **18.6** / — | 45.9 / — | 46.0 / — |
| `GET /health` | — / **23.2** / — | — | — | — |

**The `br` / `id` pair is the instrument, not two results.** Their difference is what compression
costs on that route, and their *equality* is a finding of its own:

- odin-http and Tina are **identical** on `/restart` and `/filter/preview` (71.0 vs 69.3, 42.4 vs
  42.3). Nothing is being compressed — those are the SSE routes, and neither Odin port compresses
  them. Rust and Go are 6× and 2.5× apart on the same rows, so they are.
- Which means the `/restart` row is **not a runtime comparison**. 69.3 µs against Rust's 208.1 µs
  compares a server doing the render against a server doing the render *and* a brotli pass. Rust's
  own identity number, 208.1, is the one to argue with.

**`GET /` is the row where all four do the same work**, and splitting it is what makes it useful:
54.8 µs of application against 283.6 µs of encoder here, 91.5 against 955.7 in Rust. The app work is
1.7× apart; the encoder is 3.4× apart, on the same page at the same q5 settings. C `libbrotli`
against the `brotli` crate is the single biggest number in this document.

**`POST /settings` is the cleanest cross-runtime row and the easiest to skip.** A 204 with no body:
no render, no compression, no payload — routing, header parse, body read, session lookup, one JSON
unmarshal, and a status line. Pure per-request machinery, and the ranking is odin-http ~30 µs, Rust
and Go ~46 µs, Tina 18.6 µs. `GET /health` (23.2 µs) is the same measurement with the app removed
entirely, and it is *larger* than Tina's whole `/settings` request.

**Noise floor.** `POST /settings` has no body to compress, so its two cells should be equal and are
not: 28.5 µs against 33.2 µs, a **17% spread on a row where the true difference is zero**. Treat
anything under ~1.2× in this table as unresolved — which is most of what separates odin-http from
Rust once compression is out.

**Three biases, none of them corrected in the numbers above.** The odin-http row was measured solo
today; the Rust and Go pair comes from the Rust port's run, which interleaved two servers and is
~1.3× pessimistic by its own account; the Tina row is from its document, on its own session. So
"odin-http is 1.7× Rust on the app path" is really "1.7×, of which about 1.3× may be the harness".

### Where the difference actually is

Turn the pairs into a cost per request (`1e6 / rps`, µs) and split compression out of it
(`br_cost − identity_cost`):

| `GET /` | app work (identity) | brotli | brotli's share |
|---|---|---|---|
| **odin-http** (C libbrotli) | **54.8 µs** | **283.6 µs** | 84% |
| rust (`brotli` crate) | 91.5 µs | 955.5 µs | 91% |
| go (`andybalholm/brotli`) | 748 µs | 526 µs | 41% |

Three separate things are stacked in the raw table, and only one of them is a language or runtime
result.

**1. A divergence, not a win: this port does not compress SSE.** `POST /restart` runs at 14,083 with
brotli asked for and 14,423 without — the same number, because nothing is compressed either way. The
Rust port's pair is 809 and 4,806, so it *is* compressing, and 83% of that request is the encoder.
The 17× on that row is almost entirely work this port declines to do. Same for `/filter/preview`.
That divergence is deliberate and documented (README.md, "Deliberate divergences"), but it makes the
`/restart` and `/filter/preview` rows unusable as a runtime comparison.

**2. A library choice, not a language one: the C encoder.** On the identical page at identical
settings (q5, `LGWIN` 16, 256-byte minimum), brotli costs 283.6 µs here, 526 µs in Go and 955 µs in
Rust. That is the reference C `libbrotli` against `andybalholm/brotli` against the `brotli` crate,
and it agrees with the Rust port's own finding that the crate is 1.0–2.9× slower than Go's. It is
worth 3.4× on the most expensive route in the app and it is a `cargo`/`foreign import` line, not an
architecture.

**3. The genuine remainder is small, and it is not about Rust.** On the identity path — the app work,
compression removed — this port serves the page at 54.8 µs against Rust's 91.5 µs, which is 1.7×,
falling to about **1.3× after the interleave correction**. Real, modest, and roughly what a
hand-written renderer into one arena buys over another hand-written renderer into one buffer.

### The comparison that is actually clean says the opposite

The Tina column is the one measurement in this document with only one variable in it: **the same
Odin compiler, the same corpus, and byte-identical `render`, `engine`, `corpus` and `bidfilter`
packages**, differing only in the HTTP runtime. It is faster than this port on every route:

| | odin-http | tina | |
|---|---|---|---|
| `GET /` identity | 54.8 µs | 36.1 µs | tina 1.5× |
| `POST /restart` identity | 69.3 µs | 46.5 µs | tina 1.5× |
| `GET /filter/preview` identity | 42.3 µs | 19.1 µs | tina 2.2× |
| `POST /settings` 204 | 33.2 µs | 18.6 µs | tina 1.8× |

And the floor explains the shape of it: `GET /health` — routing, a header parse and a two-byte body,
no session, no JSON, no render — costs **23.2 µs** here, which is *more* than Tina's entire
`/settings` request (18.6 µs) with its session lookup, signal unmarshal and 204. The gap is not in
the app; it is per-request machinery in the server. In odin-http that machinery is, per request: a
`map[string]string` of headers whose every `headers_set` runs `sanitize_key` (lowercase, allocating),
a `bytes.Buffer` response assembled and then copied into one `nbio.send`, a `virtual.Arena` grown per
connection, and a route table matched by scanning Lua patterns in order. Tina's is a fixed egress
buffer written in place with an index-based header table. None of that is measured line by line here
— a profiler would be the next step — but the floor measurement says that is where to look, not at
the renderer.

### So: not faster than Rust in any sense worth quoting

- On the **scenario load runs**, both servers sit far below saturation with a 1–2 ms median. Ranking
  them there is ranking noise, and the two runs are three days and a different spawn rate apart.
- On the **closed-loop probe**, this port wins every row, but the two big margins are "does not
  compress SSE" and "links the C brotli". The residual runtime difference is ~1.3×.
- On **memory under load**, the Rust port is ahead: 53 MB at 400 users against 66.5 MB here. Its
  23.9 MB at rest is the number this port wins on, and at rest is not where servers live.

The honest one-line reading: **the compressor and the SSE divergence dominate everything else, and
where the runtimes can be compared cleanly — two Odin ports, one app — odin-http is the slower of
the two.**

## CORRECTION: the same probe run interleaved, and it moves the answer

Everything in the two sections above compares a number measured here against a number quoted from
another port's document. **That turns out not to be safe**, and the way to show it is to stop doing
it: all three servers started at once, one client, the routes walked in lockstep so nothing can drift
between them. `rust-baseline` is that port unmodified; `rust-tweaked` carries three experimental
changes described below.

Requests/second, `hey -n 3000 -c 4`, one reused session per server, rust on `--threads 1`:

| route | enc | rust-baseline | rust-tweaked | odin-http |
|---|---|---|---|---|
| `GET /` | br | 1,210 | 1,828 | **3,296** |
| `GET /` | identity | 17,584 | 18,877 | **19,276** |
| `POST /restart` | br | 1,068 | 1,114 | 16,279 |
| `POST /restart` | identity | 7,124 | 10,833 | **16,336** |
| `GET /filter/preview` | br | 5,503 | 11,881 | **30,122** |
| `GET /filter/preview` | identity | 36,843 | **40,747** | 29,256 |
| `POST /settings` | br | 36,503 | **40,385** | 38,757 |
| `POST /settings` | identity | 37,105 | **40,936** | 39,282 |

### What this overturns

**The cross-document numbers were wrong by up to 5×, and always in this port's favour.** The Rust
port's own table has `GET /` identity at 10,933; measured here alongside, unmodified, it is **17,584**.
`/filter/preview` identity is published at 7,576 and measures **36,843**. Its document says its run
interleaved two servers and was pessimistic; that turns out to have been an understatement.

So the claims made earlier in this file are corrected as follows:

| claim (cross-document) | interleaved reality |
|---|---|
| "app work 1.7× faster than Rust" (`GET /` identity) | **1.10× — a tie**; 1.02× against the tweaked build |
| "3.1× on `/filter/preview` identity" | **Rust is 1.26× FASTER**, and 1.39× tweaked |
| "~1.5× on the 204 no-op" | **a tie** (1.06×), and 1.04× the other way once tweaked |
| "3.0× on `/restart` identity" | **1.51× tweaked** (2.3× against baseline) — the one route where this port is genuinely ahead |

**The application-work advantage this document claimed does not exist.** On three of the four routes
odin-http and axum are within a few percent of each other, and on the filter route axum is ahead. The
only surviving app-side gap is the fat-morph SSE route, and even that halves once the Rust port is
tuned.

What survives untouched is the part that was never about the runtime: **`GET /` with brotli, 3,296
against 1,828 — 1.80×, the C encoder against the `brotli` crate** — and the SSE rows, where this port
compresses nothing and the comparison is meaningless by construction.

### Noise, and why the interleaving matters

Within one session the instrument is tight: `POST /settings` has no body to compress, so its two
encodings must be equal, and they read 38,757 / 39,282 — **1.4%**. Across sessions it is not:
odin-http's own `/filter/preview` was 23,668 in the solo run above and 29,256 here, **24% apart on
the same binary and the same route**. That is the whole error bar of the earlier tables, and it is
larger than most of the differences they reported.

### The three tweaks, and what they bought

Applied to the Rust port as an experiment (`git diff apps/datastar-quiz-rust` shows them; the 23
tests still pass):

1. **`Builder::new_current_thread()` when `--threads 1`** (`src/main.rs`) — the multi-thread
   scheduler pays for work-stealing queues and cross-thread wakers whether or not a second worker
   exists.
2. **mimalloc as the global allocator** (`Cargo.toml`, `src/main.rs`) — Rust's Windows default is the
   system heap.
3. **`HeaderValue::from_static` for constant headers, and a non-allocating case-insensitive scan
   instead of `query.to_ascii_lowercase()`** (`src/web/handlers.rs`).

| route | gain |
|---|---|
| `GET /filter/preview` br | **+116%** |
| `POST /restart` identity | **+52%** |
| `GET /` br | **+51%** |
| `POST /settings` (both) | +10% |
| `GET /filter/preview` identity | +11% |
| `GET /` identity | +7% |

Roughly **+10% on the cheap routes and +50–116% on the allocation-heavy ones** — the streams and the
compressed responses, which is exactly where a faster allocator and a cheaper scheduler should land.
The three changes are half a dozen lines and one dependency. Which of the three does the work is not
separated here; the natural next step is to A/B them individually.

**The honest reading of this section: a pre-release, feature-light Odin server and a tuned axum stack
serve this app at the same speed, and the differences that survive are a compression library and a
compression divergence.**

## The one thing the Rust port wins, and why — measured

53 MB at 400 users there against 66.5 MB here. That is the only row in this document where this port
loses, so it is worth knowing what it is made of rather than attributing it to "no GC".

**Method.** Open N keep-alive sockets, send ONE request on each, hold them, sample the server's
working set (`tools/conn_cost.py`, in the scratchpad shape it was measured in). The per-connection
figure is the slope, and it is dead linear:

| one request per connection | body | **resident per connection** |
|---|---|---|
| `GET /health` | 2 B | **~0.1 KB** |
| `GET /sfx/correct` | ~6 KB | **9.2 KB** |
| `GET /` (default variant) | 20,102 B | **102.5 KB** |
| `GET /?swedish` (largest page) | 24,517 B | **114.7 KB** |
| `GET /static/app.css` — no render at all, `body_set` of an embedded slice | 43,388 B | **133.0 KB** |

500 connections × 102.5 KB puts the process at 73.4 MB; closing them returns it to 24.7 MB. And the
model predicts the load run: 23.3 MB + 400 × 102.5 KB ≈ 63 MB against the 66.5 MB measured at 400
users. So the whole of this port's memory under load is **per-connection high-water, retained until
the connection closes**.

**The mechanism is the arena, not the app.** odin-http gives every connection a growing
`virtual.Arena` and calls `free_all` on it after each response — which resets the bump pointer and
**keeps the block committed**. So a connection's resident set is the largest response it has ever
produced, for as long as it stays open, and a bump arena never reuses a freed intermediate: every
capacity a `bytes.Buffer` passed through on its way up is still there. The `/static/app.css` row is
the proof, because this app does no rendering on it at all: 133 KB resident for a 43 KB body is 3×
the payload spent entirely inside odin-http's own response path.

**But the per-connection slope is not most of the gap, and saying so would be wrong.** Fitting the
Rust port's own published RSS-against-users table (53 MB at 400, 99 at 1,000, 204 at 2,000, 361 at
4,000) gives a slope of **~86 KB per user and an intercept of ~19 MB** — derived from its numbers,
not measured here. Against this port's measured 102.5 KB per connection and 23.2 MB at rest, the two
halves of the 13.5 MB gap at 400 users are:

| | odin-http (measured) | rust (derived from its table) | |
|---|---|---|---|
| baseline, serving nothing | 23.2 MB | ~19 MB | **+4.4 MB here** |
| per connection | 102.5 KB | ~86 KB | **+17 KB here (1.2×)** |
| → at 400 users | 64.2 MB predicted, 66.5 measured | 53 MB | |

So it is roughly half fixed and half per-connection, and the fixed half has a name: **the brotli
arena.** Booted RSS with the encoder compiled in is 23.2 MB and without it 17.2 MB — **6.0 MB**, an
8 MB arena this port allocates once and keeps so that compression never reaches the heap, plus the
brotli copies of the nine pre-compressed assets. Take it away and this port's baseline is *below*
Rust's derived one.

That is the trade stated exactly, with both halves measured: **6.0 MB of resident memory at rest here
against ~955 µs of encoder per compressed page there.** Rust creates its encoder per response and
drops it, which costs nothing at rest and is the slowest brotli of the four ports; this port and Tina
buy the arena once. Neither is ownership-versus-arenas in the abstract, and the remaining
per-connection 1.2× is the part that really is the arena keeping its high-water block.

The Tina port sits at the third corner: 63 KB of egress plus 56 KB of route state per connection
SLOT, reserved at boot whether or not anyone connects — a bigger number, known in advance, that does
not move under load.

**One knob of it was ours, and it is now tuned.** `DOCUMENT_CAPACITY` — the builder the index
document is rendered into — is paid per connection in full, because the builder is allocated from
that same arena:

| `DOCUMENT_CAPACITY` | resident per connection (`GET /`) |
|---|---|
| 40 KB (as first written) | 110.0 KB |
| **32 KB (now)** | **102.5 KB** |
| 24 KB | 94.0 KB |

24 KB is the tempting one and is **wrong**: the swedish variant's page is 24,517 B, so it would grow
— and growing inside a bump arena is the worst case available, stranding the whole old capacity and
committing a doubled one. 32 KB is the largest page plus ~30%, which is why the constant is a
measurement with the variant sizes written next to it rather than a round number.

The rest of the gap is odin-http's, and closing it means either decommitting the arena between
requests or writing the response into a reused fixed buffer — which is, precisely, what Tina does.

## One unexplained exit

During the first attempt at the probe above the server process disappeared: `/health` refused the
connection and no `main.exe` was running. It was **not reproduced**. A rerun of the identical
sequence was clean, and a 360,000-request sweep after it — six rounds of eight routes at
`hey -n 5000 -c 8`, including the assets, the sounds and both encodings — survived every round with
`/health` answering after each. No stderr, no backtrace (the release build has the segfault handler
compiled in and printed nothing, though that run was started without a captured stderr, which is why
the reruns were not).

Recorded rather than dropped, because a server that exits once under load and cannot be made to do it
again is exactly the shape that gets dismissed and then reappears in production. If it recurs, the
first thing to do is run `just dsoh serve-brotli-debug` under the same sweep so the bounds checks and
the backtrace handler are armed.

## What this port does NOT measure

- **Multi-thread.** `just serve-all-cores` runs and is correct — the session store takes its mutex —
  but the numbers above are all one thread, which is the comparison's budget. What a global lock
  costs when eight loops contend on it is a real question and is not answered here.
- **Compressed SSE.** Not implemented, deliberately, and for a different reason than the Tina port's;
  see README.md, "Deliberate divergences".
- **A memory ceiling.** There isn't one to quote. The arena grows per connection and is freed per
  response, so the honest statement is the pair of measurements above (23.9 MB at rest, 66.5 MB at
  400 players, 95.6 MB at 800, 71.1 MB after 40,000 requests at concurrency 1,000) rather than a
  number in the source. That is the mirror image of the Tina port, which can state its ceiling exactly and pays for
  it whether or not anyone connects.
